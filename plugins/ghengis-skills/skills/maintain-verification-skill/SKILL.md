# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a skill generated by `create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the **feature**, not every sentence: cover every feature file from source and exercise every feature live, without turning every bullet into a terminal command.

## When to Use

- Periodically, or after several user-facing changes landed
- When a verify run failed and the cause might be the skill, not the app
- Before relying on the verify skill as a gate (`auto-validate`, `adw`, `gauntlet`)

## When NOT to Use

- No verify skill exists → `create-verification-skill`
- The app itself is broken and needs fixing → `systematic-debugging` (this skill only reports product gaps)

## Outcomes

Pick one, and say which:

- **clean** — every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed** — one set of proven doc, harness, or map corrections, prepared as one branch / PR. Commit and push only with the user's go-ahead.
- **blocked** — coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own directory (its SKILL.md, `features/`, and scripts it owns). **Never edit product code during a run.** A behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it; don't paper over it in docs).

## Pass

0. **Locate the target.** The project-local skill with launch/drive sections and a feature map, usually `verify-*/` under `.claude/skills/`, `.pi/skills/`, or `.agents/skills/`. A pi entry that links to a `.claude/skills/` folder is the same skill, not a second candidate. Several real candidates → ask which. None → stop and point at `create-verification-skill`; don't invent a target.

1. **Index hygiene.** Read the feature-map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Lightweight; no generated inventory.

2. **Source wave.** Dispatch one read-only subagent per feature file, all concurrently (Claude Code: Agent tool; pi: subagent tool). Each answers "how does this user-facing feature work?" from source (the `how` method), flags likely doc drift with citations, and returns one concise live-verification recipe. Children never drive the app and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn (`git log --since=<last run> --stat`) for user-facing surfaces missing from the map; require a concrete source path before calling one missing.

4. **Live pass.** Required even when source looks clean. The coordinator (you) owns all driving. Follow the verify skill's own launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs. The skill's Launch section decides, not this one. Exercise every feature at least once, and hold three invariants the whole pass, whatever fails:
   1. **Never drive an unhealthy instance.** Doctor before the first drive, on each fresh session where sessions are the unit, and again after any failed drive. Where doctor can't see the failure (a wedged UI on a healthy process), reset to a known state or relaunch rather than hoping.
   2. **Evidence survives every cleanup**, checked at its named location, not assumed.
   3. **Nothing a drive started outlives its usefulness.** Clean failed-iteration residue whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance).

   A doctor failure caused by skill drift is drift: fix it under edit scope and retry once (restart only what the fix invalidated) before calling the pass `blocked`. A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, hardware, external state) and the route attempted; if the map omits that prerequisite, that is drift. Any harness fix from triage is re-driven live before it ships. Final teardown happens after the last drive, including those re-proofs; evidence stays.

5. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it (scripts executable, invocation in the skill body). App behavior that is actually broken → product gap: record it for the user, keep it out of this change set.

6. **Ship or stop.** For **changed**: re-read every changed file, prepare one branch / PR of proven corrections, and commit/push once the user says go. For **clean** or **blocked**: no PR; report the outcome and the coverage honestly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.

## Anti-Patterns

| Anti-pattern | Why it fails | Fix |
|---|---|---|
| Skipping the live pass because source looks clean | Source reading misses runtime drift | Live pass is required |
| Fixing product code "while we're here" | Out of scope; hides regressions | Report product gaps; edit only the skill dir |
| Rewriting the map to match broken behavior | Papers over a regression | Broken behavior is a product gap, not drift |
| Subagents driving the app in parallel | Collisions on a shared instance | Source wave is read-only; coordinator drives |
| Calling a feature unreachable without a prerequisite | Unverifiable claim | Name the prerequisite and the route tried |
| Several PRs, or unproven edits in the PR | Review burden, untrusted fixes | One change set; every fix re-driven live |
| Committing or pushing without the user's go-ahead | Violates the user's commit rule | Prepare, report, wait for "go" |
| Cleanup that eats evidence | No proof left | Check artifacts at their named location after teardown |
